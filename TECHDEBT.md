## Высокий приоритет

### Локализация обработки персональных данных (152-ФЗ)

**Проблема.** Форма контакта отправляет данные через Formspree (США), сайт хостится на Cloudflare (США). По ст. 18 ч. 5 152-ФЗ операторы, обрабатывающие ПДн граждан РФ, обязаны хранить и первично собирать их на серверах в РФ. Наша текущая архитектура этому не соответствует — риск претензий Роскомнадзора, штраф до 6 млн ₽ за первое нарушение (ст. 13.11 КоАП, редакция 2024+).

**Что нужно исследовать/переделать.**
- Уточнить, применяется ли требование к физическому лицу без ИП/ООО, обрабатывающему единичные обращения (спорная зона — Роскомнадзор трактует расширительно).
- Заменить приёмник форм на локализованный в РФ сервис: [SendPulse](https://sendpulse.com/ru), [UniSender Go](https://unisender.com/ru/), собственный endpoint на VPS в РФ (Selectel, Timeweb, Yandex Cloud), или прямо через SMTP на почтовый ящик в yandex.ru / mail.ru.
- Рассмотреть перенос хостинга на РФ (Selectel Object Storage, Yandex Cloud Object Storage, Timeweb Cloud) — если данные о посетителях (IP, cookies) тоже считать ПДн.
- Разослать «уведомление об обработке ПДн» в Роскомнадзор через [pd.rkn.gov.ru](https://pd.rkn.gov.ru/) — обязательно с 30.05.2025 для всех операторов ПДн, включая физлиц.
- Пересмотреть Политику конфиденциальности и Согласие после смены инфраструктуры.

**Пока сайт работает как есть**, риск минимальный (нулевой трафик, физлицо, ничтожный объём данных), но перед публичным продвижением или запуском платного трафика вопрос закрыть обязательно.

### Убрать временный редирект `/case-template` (после 2026-09-01)

`case-template.html` — заготовка с **выдуманными** цифрами (×2,4, −38%, +61%) и **выдуманным** отзывом «Собственник, отзыв после 7 месяцев». Из сборки убрана (коммит `7dfcfb3`), файл остался в репозитории как заготовка и помечен комментарием в первой строке.

**Чего не хватило.** Удаления из сборки оказалось мало. Cloudflare Pages держит собственную копию страницы по этому адресу с `cache-control: public, s-maxage=604800`, и **зональный Purge Cache её не достаёт** — ответ приходит с `cf-cache-status: DYNAMIC`, то есть зональный кэш в обслуживании этого адреса не участвует. Владелец сделал purge 25.08.2026, `age` не сбросился и продолжил расти. Диагностический признак: тот же URL с любым query-параметром отдаёт `404` (в деплое файла нет), а чистый — `200` из кэша.

**Что сделано вместо.** В `public/_redirects` заведено правило `/case-template  /  301`. Оно едет вместе с деплоем и не зависит от состояния кэша.

**Что осталось.** После 2026-09-01 (неделя с момента кэширования) правило можно убрать — к тому времени копия истечёт сама. Проверить перед удалением: `curl -sI https://a-bra.ru/case-template` без правила должен давать `404`.

**На будущее.** Удаление страницы из сборки на Cloudflare Pages **не** делает её недоступной сразу: копия живёт до недели, и зональный purge на неё не действует. Если страницу надо убрать наверняка — сразу заводить правило в `public/_redirects`, а не полагаться на удаление файла.

### Разобраться с AI Crawl Control в Cloudflare

**Что обнаружено (2026-08-25).** В `https://a-bra.ru/robots.txt` отдаётся не только наш файл. Cloudflare подмешивает собственный управляемый блок между маркерами `# BEGIN Cloudflare Managed content` и `# END Cloudflare Managed Content`. В репозитории его нет — он добавляется на лету на стороне Cloudflare.

Что в этом блоке:

```
User-agent: *
Content-Signal: search=yes,ai-train=no,use=reference
Allow: /

User-agent: GPTBot            Disallow: /
User-agent: ClaudeBot         Disallow: /
User-agent: Google-Extended   Disallow: /
User-agent: CCBot             Disallow: /
User-agent: Bytespider        Disallow: /
User-agent: Amazonbot         Disallow: /
User-agent: Applebot-Extended Disallow: /
User-agent: meta-externalagent Disallow: /
User-agent: CloudflareBrowserRenderingCrawler  Disallow: /
```

**Что это значит.** Перечисленные краулеры собирают контент для обучения и для ответов ИИ-ассистентов. `Content-Signal` — формат Cloudflare, которым сайт заявляет: обычный поиск разрешён (`search=yes`), обучение моделей запрещено (`ai-train=no`), использовать как справочный источник со ссылкой можно (`use=reference`).

**Важно не перепутать.** Обычную поисковую индексацию это не трогает — `Googlebot` и `YandexBot` в списке нет, сайт в Google и Яндексе индексируется как обычно. `Google-Extended` — это не поиск, а отдельный агент для обучения и ответов Gemini.

**В чём собственно вопрос для владельца.** Позиционирование — консультант, продающий экспертизу. Упоминания в ответах ChatGPT, Perplexity и подобных сервисов — это потенциальный канал заявок, ровно та аудитория, которая ищет «архитектора систем роста» и спрашивает у ассистента, а не у поисковика. Текущая настройка этот канал закрывает. Обратная сторона — тексты сайта не уходят в обучающие выборки. Что важнее — решение владельца, не техническое.

**Что проверить в панели.** dash.cloudflare.com → домен `a-bra.ru` → раздел **AI Crawl Control** (в старых интерфейсах мог называться AI Audit / Bot Management). Посмотреть, включено ли это по умолчанию или кем-то настроено, и какие агенты в блок-листе. Cloudflare с 2025 года включает блокировку ИИ-краулеров для новых доменов по умолчанию — вероятнее всего, это оно и есть, а не осознанная настройка.

**Побочная техническая проблема.** В итоговом `robots.txt` теперь **две группы `User-agent: *`** — одна из блока Cloudflare, вторая наша. По спецификации robots.txt поведение при дублирующихся группах не определено однозначно: одни краулеры их объединяют, другие берут первую подходящую. Наша группа с директивой `Sitemap:` идёт второй. Стоит либо убрать свою группу `User-agent: * / Allow: /` как дублирующую (директива `Sitemap:` от группы не зависит и работает сама по себе), либо отключить управляемый блок в панели — но сначала разобраться с предыдущим пунктом.

## Низкий приоритет

### Редиректы с `a-bra.online` и `wwwa-bra.ru` не работают по HTTPS

Оба домена оплачены до 24.08.2027 и должны вести на основной сайт. Сейчас на них стоит переадресация nic.ru, и она работает наполовину:

| | `http://` | `https://` |
|---|---|---|
| `a-bra.online` | 302 → `http://a-bra.ru/` | не отвечает |
| `wwwa-bra.ru` | 302 → `http://a-bra.ru/` | не отвечает |

**Две проблемы.** Во-первых, у переадресации nic.ru нет SSL-сертификата, поэтому `https://` не открывается вообще — а современные браузеры пробуют HTTPS первым, и пользователь может увидеть ошибку вместо редиректа. Во-вторых, код 302 означает «временно»: поисковики по нему не передают ссылочный вес и продолжают считать домены самостоятельными. Для постоянного переезда нужен 301.

**Как чинить** (проделать для каждого домена):

1. Cloudflare → Add a site → **Connect a domain** → план Free → сразу Continue to activation.
2. Сменить NS у регистратора на выданные Cloudflare, старую переадресацию в nic.ru отключить.
3. Дождаться статуса Active.
4. **Создать заглушку в DNS** — неочевидный, но обязательный шаг. Redirect Rule срабатывает только на трафике, реально прошедшем через прокси Cloudflare; без DNS-записи домен никуда не резолвится и правило не применяется. Поэтому: DNS → Records → Add record → тип `A`, имя `@`, адрес `192.0.2.1`, **Proxy status: Proxied** (оранжевое облако). `192.0.2.1` — адрес из зарезервированного диапазона TEST-NET-1, он никому не принадлежит и никуда не ведёт; нужен чисто чтобы Cloudflare принял запрос на себя, до реального соединения дело не дойдёт.
5. Rules → Redirect Rules → Create rule: **All incoming requests** → Target URL `https://a-bra.ru` (статический, без `${1}` — на старых доменах никогда не было своих путей), Status code **301**, **Preserve query string** включить.

**Почему не сейчас.** Домены защитные, прямого трафика на них нет — HTTP-редирект хоть как-то работает. Приоритет вырастет, если начнётся платное продвижение или домены где-то засветятся в офлайн-материалах.
